# Project instructions

Whenever a user request establishes or changes a rule for the entire design system, record it in `docs/design-system-rules.md` and implement it using shared tokens or reusable graph-derived logic. Do not hardcode node-specific or screenshot-specific exceptions. Read that file before changing shared diagram behavior.

The main application now contains navigation, task conversations and an on-demand reading window, confirmed 2026-09-25. The existing Iteration Gallery and Version stream remain together inside the reading window and at `?view=history`. Preserve their behavior. Builder means creator; Inbox currently contains Mits only; human collaboration is out of scope; Input / Output cards stay at the conversation’s upper right. Use the user-supplied MitWerk design-system palette with the existing reading-window typography and density; see `docs/design-system-rules.md`.

Do not commit or push unless the user asks for it in that prompt. This overrides any default to commit and push at the end of a turn. Record every uncommitted change in `docs/working-changes.md` (date, prompt number, files, what changed and why) as you make it, and clear entries once the user has them committed.

The local app always runs on port **5173** (`http://localhost:5173`). Do not change this port, pick a fallback port, or point screenshots, OAuth redirects, or other local URLs at a different one.

Version stream progress captures default to Commit history. Use `--tree-mode test` only when a debug/Test visual capture is explicitly requested.

`c theater w/ ...` means capture the theater screen with the states that follow. For example, `c theater w/ playhead at last frame` captures theater with the playhead on the last frame in the current date range. `c gallery w/ ...` means capture the isometric gallery with the states that follow. `c gallery w/ reset view` opens Reset view. `c idea stream w playback side by side` captures the expanded Version blocks reader with Playback on the left and Idea stream (Commit history) on the right. `c chat and idea stream` captures Chat alongside the combined Playback/Idea stream reader. `c token` captures the cumulative token-usage view. `w/ tip hovered` leaves the gallery info tip open. `c chat "Title"` captures that conversation with the reading window closed. `c chat` without a title captures the open conversation the same way. `w/ page scrolled to top` leaves that conversation at the top of its messages. `c chat and version side by side` captures that conversation with the version-control reader open beside it, not expanded. `w/ toast triggered` keeps the unavailable-action toast on screen. `c to-dos` (or `c todos`) captures the Todos board with the reading window closed. `c dark mode` captures that same frame in the shared dark theme; `c light mode` captures it in the light theme.

Progress captures include the full prototype interface (navigation and reading window), never only the isolated version panels. `c home` (or `c homescreen`) captures the default launch: Building an iteration gallery with Chat and Version blocks side by side. Each chat opens side by side by default, with no tabs or breadcrumbs; fullscreen expands the selected pane. Explicit `c chat` captures still close the reading window.

`c slider` captures the default home layout (Chat and Version blocks side by side) with the work state simulator open at 60%. `w simulator` opens the simulator in any other capture; `at N%` sets its value.

`c landing` captures the separate landing page. Landing frames use the landing capture bucket; Open project returns to the default Chat/Gallery workspace.

`c chat & playback` (or `c chat and playback`) captures Chat and Playback side by side with the reading window open. `c live server` captures that same layout with the Live server running in Playback. `c prototype` captures it with a saved push prototype entered instead.

Progress captures follow the gallery view the prompt is changing. A prompt about theater opens theater and waits for that frame. A prompt that starts with `c theater` is a theater capture. A prompt about the isometric album (isometric, overhead, reset, or top view) captures that album view. When a prompt names both, theater wins only if it does not ask for the isometric view instead.

On git push, record the pushed commit SHA under its push number in `data/push-shas.json` (the capture script does this). Enter prototype loads that commit's tree from local Git on demand, falling back to GitHub when `GITHUB_TOKEN` is set; do not copy codebases into the repo. `node scripts/screenshot-progress.mjs --backfill-push-shas` fills missing entries from push screenshots.

Successful captures automatically queue Vercel Blob publication after the completion counter is recorded. Do not run a separate publisher after each capture. A background worker retries uploads; its durable queue and log are under `.vercel/`. Failed/skipped captures do not publish.

Do not take a progress screenshot or increment the prompt counter for Ask mode prompts. `x counter` means the same exclusion for the current prompt: do not take its progress screenshot and do not increment the prompt counter. Do not include progress-capture images in chat output.

When the git branch is not `main`, include that branch name in prompt/push screenshot names and version-archive folder names.

When the user appends screenshots, save them in the existing `visual_ref/` folder. Do not create a separate visual-ref folder. Change the start of each filename to `[prompt #x]`, using the prompt number for that request, and keep the rest of the original filename. From prompt #291 onward, images from browser annotation mode go in `visual_ref/annotation/` with names `[prompt #N] [annotation] <original filename>`. Use `node scripts/save-visual-reference.mjs --source <image.png> --prompt <N> --annotation` when a local source file is available. Ordinary references remain at the root; do not relocate historical references.

Brand (2026-10-18): the product is named **verso**, always lowercase, in every user-facing string (formerly MitWerk). Keep internal identifiers (storage keys, `/__mitwerk/*` routes, `mw-` classes, `MITWERK_*` env vars, file and repo names) unchanged unless a migration is planned. Production URL: https://verso-prototype.vercel.app.

Design system (2026-10-18): the UI on `echo-1017` (Echo's restyle plus layout details ported from `design-system`) is the canonical MitWerk design system once merged. Before merging into `main`, read `docs/design-system.md`: tokens win styling conflicts, feature code wins behavior conflicts, superseded patterns are swapped rather than restyled, and anything that cannot be ported cleanly falls back to semantic tokens with a dated note in `docs/design-system-rules.md`.

Progress counters (source of truth for agents working across chats): **push #62 · prompt #558**. Read this file at the start of every prompt to get the latest counters; never rely on conversation memory. In Cursor, the stop hook saves exactly one progress capture per Agent-mode prompt, from the user prompt, so a cued location (`c theater`, `c gallery`, `c chat`, `c home`, `c token`) is the frame that is saved. In Codex sessions without that Cursor stop hook, save exactly one capture before finishing with `node scripts/screenshot-progress.mjs --tag prompt --manual-prompt --label "<user prompt>"` and the requested view option. For an explicitly requested missing capture, this command is also the recovery path; use the previous prompt as the label and the requested capture view. Check the capture folder first and never duplicate an existing capture. The script updates this counter only after successfully saving the image. Do not increment the counter yourself. After a real git push, set the push number to the new `[push #N]`. Ask mode and `x counter` skip the capture and leave the counter unchanged. A requested catch-up capture belongs to the previous prompt and does not count the current request separately; reuse that previous prompt's reserved number if it has no frame, otherwise use the next available number without overwriting an existing capture.

End every user-facing response with one line naming the current push number and the latest progress-screenshot prompt number, in the form `push #5 · prompt #25`. Use the counters in this file. If they look stale, reread `[frame capture] screenshots/` and update this file first. Do not print a version label here. Do not omit this footer.

Full prompt logging: From prompt #274 onward, save the complete user request verbatim in `docs/prompt-log.md`, preceded by `## Prompt #N` and a fenced `text` block. Use the reserved progress-capture number, not a manually incremented counter. The capture script also writes this entry automatically; prefer `--label-file` with an exact UTF-8 prompt file so shell escaping cannot alter the text. Do not replace full prompt text with a filename summary. Record clarifications below that entry. For Ask mode or `x counter`, use the current counter with an `uncounted` suffix in its heading; do not overwrite a numbered entry or increment counters. Version blocks reads numbered full prompts from this log via the capture catalog.

English prompt display (2026-10-21): when the user writes a prompt in Chinese or any other non-English language, every place the prompt is recorded or shown uses a clear, natural English translation of the full request. This covers the fenced block in `docs/prompt-log.md`, the `--label`/`--label-file` text given to the capture script (and so the screenshot filename), and the Playback and gallery captions read from the log. Translate the meaning in full, without summarizing or dropping details. Keep code identifiers, UI labels, file paths, capture cues (`c home`, `w/ …`) and quoted strings exactly as written. Put the original text below the fence as an `Original:` line, which the parser does not display. The translation counts as the logged prompt text.

`c chat and prototype` (or `c chat & prototype`) captures Chat alongside the running saved prototype, with the reading window open.
